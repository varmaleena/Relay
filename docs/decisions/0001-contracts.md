# ADR 0001: canonical contracts and M0 export boundary

Status: accepted implementation choice for approved M0; 13 October 2026.

Pydantic v2 owns strict domain schemas and camelCase transport aliases. Pack YAML uses snake_case disk names; aliases round-trip both representations. Extra unknown fields are rejected. Domain legal content is not authored in M0. Dynamic named Pydantic transport models represent all E1–E43 plus four E44 method/path operations (47 total). JSON Schema, OpenAPI and TypeScript are generated deterministically by `python -m scripts.export_contracts`; `--check` fails on drift. The schema-generation module uses runtime `create_model`, with the specific mypy static-alias limitations documented locally.

The exported catalog describes future request/response contracts and role/org-scope metadata. It does not implement business endpoints or enforce runtime business authorization. The contract app returns 501 for these operations; the executable M0 health shell is separate. This distinction is visible in OpenAPI descriptions and generated client comments. Endpoint implementations and full runtime authorization tests belong to their approved later phases.

Money differs deliberately from Section 14's JSON-number shape: `value` accepts decimal numeric/string inputs under Pydantic's Decimal conversion and serializes as an exact decimal **string**, with an uppercase three-letter currency code. Large or fractional amounts cannot safely round-trip through JavaScript binary numbers. Clients should send decimal strings and treat returned values as strings. OpenAPI distinguishes validation number/string input from exact string output; generated types follow those schemas. Values must be positive, finite, at most 20 digits and eight decimal places. This is a wire-contract decision that must remain visible to future integration and UI work; no silent float coercion in financial calculations.

Packet states include NEEDS_HUMAN_REVIEW. Ambiguous classification carries clarifyingQuestion. Required packet fields have explicit availability and provenance. Completeness count and weighted score are separate concerns. DeadlineState exposes unsupported_in_v1 for business calendars. Recipient language and typology-category mapping are explicit pack fields. Human acceptance of unverified rules is recorded separately and cannot convert evidentiary status.

E19 answers require ifVersion and cannot resend. Editing/answering creates a new version; delivery uses a fresh E17 explicit confirm/current packetVersion/confirmedRecipientId approval. E24 decisions also bind packetVersion. Admin cannot approve a victim message or impersonate an institution decision. Admin may manage review content per Section 16; reviewer-org scoping still applies. Cross-org receiver projections remain separate from victim CaseView. Automatic transport receipts are not human acknowledgments.

The generated client encodes path components, supplies Firebase bearer and App Check credentials, serializes bodies as JSON, exposes optional query/header idempotency inputs, and generates a UUID for new POST intents. Retrying the same intent must retain its supplied idempotency key. It handles 204 with no body. PDF 302 is a special redirect operation; callers must navigate explicitly after human approval. No implicit external share or send is introduced.

Future API status and mutation contracts retain explicit audit/idempotency metadata. More detailed notification/history/org-management operations are deferred until their implementing phase rather than invented in this catalog. Any contract change must regenerate artifacts and pass drift, alias/precision/state and security-boundary tests.
